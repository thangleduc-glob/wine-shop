# research.md — User Authentication (user-auth)

Decision: Use Supabase Auth (email/password) with email verification disabled.

Rationale:
- Project constitution and existing stack indicate React/TypeScript and Supabase as the canonical stack.
- Supabase Auth provides a managed user store and sign-in flows, reducing scope and security risk of handling password storage directly.
- Requirement explicitly requests "config supabase auth to no need to verify email" so Supabase Auth configuration aligns with the feature.

Alternatives considered:
- Rolling a custom auth service: rejected due to increased scope and security burden (password storage, resets, hashing).
- Social login only: out of scope per spec.

Decision: Enforce client-side password strength (minimum 8 chars, at least one letter and one number) and rely on Supabase Auth for server-side validation.

Rationale:
- The project prefers using managed services for identity. Client-side enforcement improves UX and reduces obvious weak passwords before network submission.

Decision: No database schema changes for products or users in this feature.

Rationale:
- Product page intentionally empty. Supabase Auth manages user identities; no custom user table or RLS changes required.

Testing & Validation decisions:
- Use Playwright E2E to validate signup and login flows (per constitution).
- Add a quickstart.md with runnable validation steps.
